# 海外工单看板

GitHub Pages 从 `main` 分支的 `/docs` 发布前端。页面启动后，通过 HTTPS 从同步服务读取工单。实际工单、数据库和令牌保存在部署环境中。

## 同步服务

用 Node.js 24 或更新版本运行以下命令。服务默认监听 `127.0.0.1:8787`。在公司批准的常驻环境运行服务，用 HTTPS 反向代理提供访问，并把 SQLite 路径放到持久磁盘上。运行一个服务实例。

```sh
node --env-file=.env server.mjs
```

将 `.env.example` 复制到 `.env`，填入两个不同的随机令牌及 GitHub Pages 的完整来源域名。读令牌发给有权看工单的人员，写令牌只配置在来源工作流。读令牌只在当前页面内存中使用。

## 第一次接入 ShareCRM

1. 先用批准的工单报表做一次初始化。只映射四个工单类型，传工单号、类型、创建时间、当前状态、该记录的更新时间和关单时间。按需要分批，每批最多 2000 条。
2. 接入纷享销客的工作流或报表同步。新建、状态变化和重新打开的记录，都用同一个工单号发送完整字段。数据来源必须发送关单和取消记录，服务据此暂停催办。
3. 在确定已收到截至某一时刻的所有变更后，填写 `sourceAsOf`。事件推送可以随日常补偿任务发送空清单和这一时间，保证没有业务变化时也能确认链路仍正常。分批同步时，只在最后一批发送该时间。

向 `/api/sync` 发 `POST`，使用 `Authorization: Bearer <SHARECRM_SYNC_KEY>` 和 `Content-Type: application/json`。示例为虚构记录，时间字段带时区。

```json
{
  "sourceAsOf": "2026-01-04T08:30:00+08:00",
  "orders": [{
    "number": "EXAMPLE-001",
    "type": "Repair",
    "status": "In Progress",
    "createdAt": "2026-01-02T08:00:00+08:00",
    "updatedAt": "2026-01-03T15:00:00+08:00",
    "closedAt": null
  }]
}
```

支持的工单类型是 `Repair`、`Maintenance`、`Installation` 和 `FCO`。状态使用 ShareCRM 的 `Work Order Status` 字段显示值。`Closed` 和 `Cancel` 停止催办。`Closed - Pending Review` 按仍需跟进处理。重复消息和更早的更新不会覆盖较新的状态，也不会清除已提醒档位。

事件到达时间和来源的最新完整状态是两个概念。每次确认完整同步后提供 `sourceAsOf`。此时间默认超过 26 小时后暂停发提醒，并在看板标出数据滞后。按你们的数据刷新频率调整 `SYNC_MAX_AGE_HOURS`。

## 飞书提醒

配置目标群的 `FEISHU_WEBHOOK_URL` 后，后台每分钟检查一次。自然 24、48、72 小时分别提醒，消息发送成功后记录档位。首次同步或长时间停机后如果已跨过多档，只发当前档。群消息包含工单号、类型、时长和数据截至时间。飞书消息没有端到端幂等凭据，若飞书已收到但服务未收到成功响应，重试可能重复发出。

## 打开看板

打开 GitHub Pages 地址，点「连接数据」，输入 HTTPS 同步服务地址和只读访问令牌。看板每分钟刷新一次，也可手动刷新。通过浏览器查看前端与通过飞书后台发送提醒可以独立运行。
